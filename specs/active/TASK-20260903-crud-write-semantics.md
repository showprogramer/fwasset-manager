## 定稿规则

### D0 `platform` 语义裁决、目录层级与布局归一

**D0.1 新增 `FirmwareAsset.chassis_type`，`platform` 保持 legacy 只读。**

- `chassis_type` = 型号机芯类型。**`core/types.py` 定义真源** `ChassisType = Literal["单3D", "单2D", "双2D", "上3D下2D"]`，字段类型 `ChassisType | Literal[""]`。
- `platform` 语义与生产逻辑**完全不变**（`_infer_asset_context` 不改），只标注为 legacy、不再用于新功能。现有四处 UI 消费者不受影响。
- 两字段同批纳入索引，与 D6 的 `vendor` 一起一次性提升 `schema_version`（D6.4），只做一次全量重扫。

> 不采用「重定义 `platform` = 机芯类型」：该字段是索引列且有四处在用，重定义会让存量数据含义无声漂移，且 legacy 方案的 `platform` 值（如「标准单机芯3D」）与新枚举对不上。

**D0.1a `chassis_type` 生产链**（scanner 当前完全不读型号根 `平台配置.toml`，必须显式定义）：

1. 先识别每个资产所属型号根（复用 `enumerate_model_roots` / `_owner_root_for` 的归属规则）；
2. 严格读取该型号根 `平台配置.toml`；
3. **恰好一个块且 `name` 属于 `ChassisType` 枚举** → 写入 `chassis_type`；
4. `missing`、多块、非枚举 legacy name → 写 `""`；
5. **`parse_error` / `parser_missing` → 写 `""` 并产生 warning，不阻断索引对账**（扫描是最广路径，损坏一个型号的配置不应使整次扫描失败；严格阻断由 R8 反查侧承担）。

   **warning 需要可承载的公共契约**——当前扫描 API 只返回 `(assets, errors)`，而 `reconcile_subtree` 遇任何 `errors` 即拒绝写库。定稿：扫描结果统一为带 `severity: "warning" | "error"` 的 `ScanIssue` 结构；chassis 配置损坏进 warning，目录读取失败/取消进 error；**`reconcile` 只因 error 阻止**；全量与子树扫描返回同一诊断结构；
6. `scan_firmware_assets` 与 `scan_firmware_subtree` 对同一路径必须**字段级一致**；
7. 同一型号根的配置在单次扫描内缓存，避免每个资产重复读盘。

**D0.2 目录层级规范**：正式 CRUD 新增程序一律写成——

```
通用/<模块>/<程序名>/
定制/<方案>/<模块>/<程序名>/
```

模块目录**只作容器**，新数据不再产生「模块叶子资产」。平台 default 的新值一律是程序目录名；空串只保留给 legacy 数据。

> 没有这条，D0.3 的归一会永远是日常前置——新建的资产又会造出新的模块叶子。

**D0.3 legacy 布局归一（D1.4 的前置）**：legacy「模块叶子唯一程序」（如 `通用/主板程序/` 直接含程序文件）在参与 update 前，必须先做一次身份延续的归一——`通用/主板程序/` → `通用/主板程序/<程序名>/`，走 R8 `rename` 同步 `static`、`follow_asset` 与 `defaults`。

- **`<程序名>` 由用户输入**，首次归一时要求确认，经 D3 名称校验。**不得**从版本号、固件文件名或类型名静默猜测（legacy 模块叶子的目录名通常就是类型名，没有独立程序名可派生）。
- 归一是**独立操作**，不隐含在 update 内；UI 在用户首次更新此类程序时提示并请求确认。

**归一状态机**（不能直接把目录 `M` 移进自身后代 `M/V`，必须借道临时目录）：

1. 构建 asset rename `M → M/V` 的 R8 plan；
2. `M` → staging/temp；
3. 创建新的模块容器 `M`；
4. staging/temp → `M/V`；
5. apply plan；
6. `reconcile_subtree`（`M` 的父目录）。

失败补偿（全程持写锁并写持久化操作日志，D8.3）：

| 失败点 | 处理 |
| --- | --- |
| 步骤 2（`M` → temp） | 原状不变 |
| 步骤 3（创建新 `M`） | temp → `M` |
| 步骤 4（temp → `M/V`） | **仅当新 `M` 仍为空**时 `rmdir M`，再 temp → `M` |
| 步骤 5 apply 完整回滚成功 | 反向恢复目录 |
| 步骤 5 出现 `rollback_conflict` | **停止自动移动**，返回 `layout_inconsistent` |
| 任一恢复动作失败 | `layout_inconsistent` |

全部动作由事务日志记录；**不得递归清理未知内容**。
- 归一后模块目录成为容器，`_validate_target_kind` 对「含变体的模块容器」与「变体」都有明确判定。
- 归一属**身份延续**，不是新身份占用：目标路径命中的历史锚点是预期结果，走 D3 的窄化例外（仅当发现 plan 之外的重叠锚点才返回 `path_identity_conflict`），**不得泛化为用户可选的强制覆盖**。
- 未归一的模块叶子**不允许**直接 update。

### D1 改类型 / 改范围 + 普通 update 落点

**D1.1 改类型/改范围 = 独立复合操作**，不走 R8 update 级联。提交顺序（全程持写锁）：

**锁外**：影响预览与退位方式选择（D1.4b）。**用户确认后才取写锁**（D8）。锁内：

1. 全部 gate、目标校验、引用反查、新路径准入（D3）、磁盘空间检查——**全部只读，零写盘**。
2. **构建并冻结 defaults 清理计划**（D1.3），此时不执行。
2a. **计划冻结且全部 gate 通过后**，紧接第一次 staging 写入之前，创建持久化操作日志（记录 plan、旧/新路径、阶段）。日志创建失败则不执行任何产品数据变化。
3. 新程序写入 staging（D7.1），**完成 catalog 校验——replacement 必须是完整合法资产**（见 D1.5）。
4. 原子提升到最终路径。
5. 执行 defaults 清理计划。
6. 清理成功后，旧程序才退位（按 D1.4b 选择的 `retire_to_trash` / `retire_to_backup` 分支）。
7. **索引：对「旧路径与新路径的最小共同现存祖先」调用 `reconcile_subtree`**（由其扫描完整快照后单事务写入）。**不是直接调 `bulk_reindex_subtree`**——后者不扫描、要求调用方传完整 assets；只有确定为空的边界才用 `bulk_reindex_subtree(..., assets=[])`。

失败契约：

| 阶段失败 | 返回 | 状态 |
| --- | --- | --- |
| 1–4 | 常规错误码 | 清理 staging，旧程序未动 |
| 5 | `config_rewrite_failed` | 新程序已就位，旧程序未退位；两份并存 |
| 6 | `retire_failed` | CAS 恢复 defaults；恢复冲突则 `retire_failed_with_config_conflict` |
| 7 | 提示重新读取程序列表 | 磁盘为准，不回滚 |

**禁止出现「旧已退位但新程序不可用」的结果。**

**崩溃恢复**（步骤 5 后 / 6 前崩溃会留下「旧新并存但 default 已清」；6 后 / 7 前崩溃会留下旧索引）：启动时按操作日志恢复——

- 旧仍存在 → CAS 恢复 defaults，或继续退位；
- 旧已退位 → 完成索引对账；
- 检测到第三方修改 → 停止并返回恢复材料，不自动续跑。

> defaults 清理放在退位之前是较安全的顺序（失败时旧文件仍在），顺序不调整，但必须有崩溃恢复。

**D1.2 借用引用沿用删除零改写**（R8 规则 5）：旧程序的借用条目保留、解析自然 missing、撤销即恢复。

**D1.3 平台默认是本复合操作的显式例外。** 清除范围限定为反查命中的 `block_index` 对应条目。按变化种类分别定稿：

| 变化 | defaults 处理 |
| --- | --- |
| 改类型 | 清除旧 canonical 键的命中 defaults |
| 通用 → 定制 | **同样清除**精确命中的 defaults（否则复合操作结束后留下已知悬空 default） |
| 定制 → 通用 | **不自动设为默认**，由用户显式「设为默认」 |
| 定制方案 A → B | 无平台 default 改写（defaults 只指向通用区） |

**需新增受签发的计划入口**（R8 现有 `build_rewrite_plan` 遇语义变化即 `unsupported_semantic_change`，且 plan 不可手工构造）：

```
build_clear_defaults_plan(configured_root, workspace_root, old_path, change_kind) -> ServiceResult
```

**builder 内部冷读、重新反查并派生完整命中集，再签发 plan**——不接受调用方传入的 `hits`（传入不完整列表会漏清 defaults，传入过期或伪造 hit 会清错块）。持有 TOML preimage 与新内容，经 `apply_rewrite_plan` 同款 CAS 落盘、可回滚。不猜测替代者，由用户重新「设为默认」。UI 必须先展示影响。

> 与「删除零改写」的关系：删除程序不动 defaults（R8 规则 5 不变）；改类型是另一种操作，明确要求 default 失效。实现者不得混为一谈。

**D1.4 普通 update 落点矩阵**（不涉及语义变化，走 R8 update）：

| 旧资产形态 | replacement 落点 |
| --- | --- |
| 模块叶子唯一程序 | **先按 D0.2 归一**，之后按下一行处理 |
| 模块下变体之一 | staging → 提升为同模块下的**兄弟变体目录** |
| 有 static 借用指向 | 同上，且 replacement 与任一 static 锚点不得父子重叠（R8 已强制） |

不得原位覆盖，不得把旧资产变成 replacement 的父容器。退位方式（隔离区 / `旧版本/`）不影响落点规则。

**D1.4a 普通 update 事务状态机**（接入 D8.3 协调器）：

**锁外**：来源选择、影响预览、退位方式选择（D1.4b）。**用户确认后才取写锁**（D8：等待用户选择期间不得持锁）。

锁内：

1. 重验用户选择、generation、路径、引用与目标状态；
2. 创建操作日志，随后 staging 导入并**验证完整性**（D1.5：必须是完整合法资产）；
3. 提升 replacement 到最终路径（记录提升时的 manifest hash）；
4. 此时 old 与 replacement **同为现存合法资产** → `build_rewrite_plan`（R8 update）；
5. apply plan；
6. 旧程序退位（按 D1.4b 选择的分支）；
7. 对共同祖先 `reconcile_subtree`；清理日志。

失败契约：

| 失败点 | 处理 |
| --- | --- |
| **build** 失败 | 按 D1.4c 清理本次 replacement |
| apply **完整回滚成功** | 按 D1.4c 清理本次 replacement，恢复原状 |
| apply 出现 **rollback conflict** | **保留现场**，返回 `update_inconsistent`，不自动删除 replacement |
| apply 成功、步骤 6 退位失败 | 保留两份；引用与 defaults 已指向新程序；返回 `retire_failed` |

**崩溃恢复**（各阶段的启动恢复动作）：

| 崩溃点 | 恢复 |
| --- | --- |
| replacement 已提升、尚未 build | 按 D1.4c 清理 replacement，回到原状 |
| apply 成功、旧程序尚未退位 | 继续退位 |
| 旧程序已退位、尚未对账 | 只做 `reconcile_subtree` |
| `retire_to_trash` 已完成、尚未清理日志 | 清理日志即可 |

**D1.4b 退位两分支**（落点、生命周期与恢复完全不同，不得合并为一种记录）：

| 分支 | 落点 | 生命周期 |
| --- | --- | --- |
| `retire_to_trash` | 进入 `transactional_retire` 隔离记录 | 提交成功后异步送系统回收站，不展示撤销 |
| `retire_to_backup` | `<replacement>/旧版本/<旧名>-<时间戳>/`，写副本元数据（D4.2） | **不进隔离区、不送回收站**，用户长期保留 |

D1.1、D1.4a 与 D4.1 一律引用这两个精确分支，并各自列失败与崩溃恢复。

**D1.4c 「删除本次产物」统一原语**（应用锁挡不住资源管理器或其他程序往 replacement 里加文件）：清理前必须同时满足——① 路径仍是本操作创建的身份；② 当前 manifest hash 等于提升时记录的值；③ 操作日志状态允许清理。任一不满足 → **保留现场**，返回 `update_inconsistent` 及恢复材料，**禁止递归删除**。

D1.1、D0.3、D2.1 中所有「删除本次产物」的补偿**复用同一原语**——复用的是**身份、manifest 与日志状态校验**；D2.1 的实际动作仍是「逐文件 CAS 删除 + 逐层 `rmdir`」，**不是对型号根做递归清理**。

**D1.6 「仅改厂商、不换文件」的 update**（原型明确允许，不放入新程序时不问旧程序去向）：

- **不走 R8 update**（资产身份未变）；
- 严格读取并合并 `程序信息.toml`，**保留未知键**；preimage/CAS 原子写；
- 持写锁与 generation；统一 configured-root gate；
- 元数据**解析损坏** → 保留原文件（D6.2），返回 `metadata_corrupt`；**文件缺失按合法空文档处理**，不是损坏；
- **新值与旧值相同 → 返回 `unchanged`，不写盘、不递增 generation**；
- **不触碰程序目录、引用、defaults 与资产身份**；
- 索引：**对当前资产目录执行保留上下文的扫描**，按 `same_path_identity` 选出且只能选出一个目标资产，再 `replace_asset(old_path, scanned_asset)`——**不得由调用方手改 `vendor` 字段拼出资产行**；索引行缺失或 replace 失败 → 元数据保留、以磁盘为准，返回 `index_update_failed` 并提示重扫；
- 不可撤销（D10.2）。

**D1.7 「设为默认」的写语义**（正式程序 CRUD 的核心写入口，不能留给 UI 猜）：

- 目标必须是**本型号通用区的完整合法资产**；
- **已归一 gate**——「单块」不等于「已归一」（一个名为 `默认` 或 `标准单机芯3D` 的 legacy 单块会被放过）。要求三条同时成立：① 恰好一个 block；② block name 属于 `ChassisType`；③ 目标 canonical 键**既无异值冲突（`canonical_conflict`）也无同值别名（`canonical_duplicate`）**。否则返回 `platform_not_normalized`；

  > 同值别名也必须拒绝：否则同一模块同时存在 canonical key 与 alias 时，设默认没有规定该写哪一个、是否合并。「设默认只接受已归一配置」的定义要求这里从严。
- **残留 `follow_default` 检查**：设默认会立即改变依赖该来源型号/模块的 legacy `follow_default` 指向。设默认前反查——全部已迁移则正常写；仍有命中则展示影响并阻止，返回 `follow_default_migration_required`。**不得静默改变**；
- variant value 由目标程序目录名派生（D0.2 后一律是程序目录名，空串只留给 legacy）；
- 严格读取 + preimage/CAS 写 `平台配置.toml`；
- 持写锁与 generation；统一 configured-root gate（见下）；
- **不可撤销**（D10.2，替代路径是重新设为原来那个）；
- TOML 写成功但后续刷新失败 → 磁盘为准，提示重新读取，不回滚。

**与现有 `platform_default_service` 的替换关系**（当前 `set_module_default_for_model` 会 `ensure_platform_blocks` 并更新所有块；`set_default_variant` 找不到块时会创建新块；两者都没有 configured-root gate、写锁、generation 与 preimage CAS）：这两个入口**改造或降为内部 helper**，正式产品只走新的单块受管服务，**禁止 UI 继续直接调用旧行为**。

> D1.6 / D1.7 与借用服务（`shared_module_service`）都须**显式接入统一 configured-root gate**——现有服务只有 workspace path guard，没有 R1/R10 的配置根相等性校验，旧 UI 调用点可能绕过 gate。

**D1.8 登记 / 覆盖借用的写契约**（直接改写 `型号配置.toml`，属 CRUD gate 必须覆盖的写入口）：

- 严格加载 + 统一 configured-root gate + 写锁 + generation；
- 来源必须是**完整合法资产**，且不在任何受管排除路径内（`旧版本/`、staging、隔离区——见 D4.4 `retired_anchor`）；
- `static` / `follow_asset` 的构造与序列化（`follow_default` 不再新产生）；
- 同 canonical module **已有登记时，必须展示并显式确认替换**（原型规则：再记要确认覆盖）。**覆盖确认有 TOCTOU**：用户在锁外确认覆盖条目 A 后，另一进程可能已把它改成 B。锁外预览须记录原条目的规范身份、内容指纹与 generation；**锁内三者仍一致才允许写**，否则返回 `stale_plan` 并重新展示影响——**不得基于最新内容直接覆盖**用户从未确认过的条目；
- preimage/CAS 写入，**保留无关 raw key 与未知字段**；
- 错误码：`canonical_conflict`、并发修改（`stale_plan`）、写后刷新失败；
- 另见 D9.2a：`self_reference` 与 `no_other_model` 由 service 独立校验；
- **登记不可撤销**（D10.2）；解除借用产生 D10.1a 的受签发 undo 数据。

**D1.5 replacement 完整性要求**（与 D7.5 的分界）：

- **普通新增**允许 `created_incomplete`（原型规则，手控 UI 缺文件不阻断）；
- **update / 改类型 / 改范围的 replacement 必须是完整合法资产**；
- incomplete replacement 只保存为独立待补齐项，**复合操作立即结束**——defaults、引用、旧程序**均不变**；
- 用户补齐后**重新发起** update，不自动续跑旧计划。

### D2 型号 / 方案创建、重命名、删除

> **前置：型号级操作作用于稳定工作区下的型号目录；旧布局先完成 D9.3 迁移。工作区允许零个型号，不因型号数量禁用新增，见 D9。**

**D2.1 新建型号**（全程持写锁；`model_id` 枚举、占用检查与 TOML 原子写必须在同一次锁持有期内）：

1. 新路径准入（D3）。
2. 在工作区下创建型号根 → `通用/` → `定制/`，逐个记录本次成功创建的条目；允许零型号工作区创建首个型号。
3. 写 `型号配置.toml`（`model_id` = `slugify_model_id(目录名)` + 工作区内唯一性去重）。
4. 写 `平台配置.toml`（D5.1，单块）。
5. `bulk_reindex_subtree` 建索引。

**回滚（2–4 失败）**：按创建记录逆序撤销——TOML **仅在当前字节仍等于本次写入内容时**删除；子目录一律 `rmdir`（仅空目录可删），**绝不递归删除**；型号根最后 `rmdir`；遇外来内容返回 `rollback_conflict`，保留现场并给出恢复清单。

步骤 5 失败：磁盘保留，提示重新读取，不回滚磁盘。

**D2.2 新建方案**：与型号同粒度。`方案配置.toml` 规范内容为 `name = "方案目录名"`，**不写 `platform`**。已存在同名空目录不复用，按 `path_exists` 拒绝。回滚同 D2.1。

**D2.3 重命名型号/方案/模块/程序**（全程持写锁）：

1. 新路径准入（D3）。
2. **构建复合配置计划**：R8 改写项 + **方案自身 `方案配置.toml` 的 `name` 新内容**一并持有 preimage/CAS，**统一 apply**。不得把方案 `name` 写入做成 plan 外的独立动作（否则「R8 已改写成功、目录已在新路径、name 写失败」这一态没有补偿契约）。
3. 移动目录。
4. apply 复合配置计划。
5. 索引：对**移动前后最小共同现存祖先**调用 `reconcile_subtree`（只对新路径对账会留下整棵旧索引）。

失败契约：

- 步骤 4 **完整回滚成功** → 回移目录，返回 `rewrite_failed`；
- 步骤 4 返回**任何 `rollback_conflict`** → **停止自动回移**，直接 `rename_inconsistent`（回移可能把第三方已修改的配置一并移回，或使 TOML 与物理路径进一步不一致）；
- 回移本身失败 → `rename_inconsistent`；
- payload 必须含物理目录位置、已改/已回滚/冲突文件清单与恢复材料；
- 步骤 2–4 间检测到并发修改 → `stale_plan`（R8 已有）。

**D2.4 删除型号/方案**：

1. `find_references_to(target, "model"|"scheme")` 反查。
2. 影响列表全部展示；**「必须勾选」条件限定为跨 owner 的 shared 命中**——本型号自身随目录一起删除的 defaults 不是外部借用。
3. 移入隔离区（D2.5）。
4. **零 TOML 改写**（R8）。
5. 索引：`bulk_reindex_subtree(workspace_root, deleted_root, assets=[])`。**不是 `delete_asset`**。索引失败保留磁盘结果并提示重扫。

撤销：隔离区移回成功后对原边界执行 `reconcile_subtree`；失败则保留目录并提示重扫。恢复属原身份延续，不触发 `path_identity_conflict`，但目标已被其他内容占用时必须阻止（`undo_conflict`）。

空型号与空方案保留显示，由用户显式删除；型号是否存在不依赖资产索引。删除最后一个型号仍保留配置根，进入可新增型号的空工作区；撤销时恢复型号子目录。

**D2.4a 删除程序**（asset 级，最常用的删除操作）：

1. `find_references_to(target, "asset")` 反查；阻断级 issue 一律阻止。
2. 影响列表全部展示；有跨 owner 的 shared 命中时必须勾选确认（同 D2.4）。
3. 移入隔离区（D2.5）。
4. **零 TOML 改写**（R8）——借用条目保留、解析自然 missing、撤销即恢复。
5. 索引：`bulk_reindex_subtree(workspace_root, deleted_asset_path, assets=[])`（该边界确定为空）。
6. 撤销（D10.1）：隔离区移回 + 原边界 `reconcile_subtree`；目标被占用 → `undo_conflict`。
7. **删除最后一个变体后的空模块容器：自动删除，但仅可用 `rmdir`**——遇任何内容（含 `旧版本/`、`程序信息.toml`）一律保留，不递归删除。
8. 模块容器被删除时，**最终对模块父级再做一次 `reconcile_subtree`**，保证 firmware-type / model 级 `hidden_items` 不残留（程序边界先清空、容器随后才删，两步之间隐藏项可能失去归属）。

**删除确认必须展示副本影响**：删除包含历史副本的当前程序会连带删除其 `旧版本/` 下全部副本。确认框须明示「该程序包含 N 个备用副本，也将一并删除」——否则用户可能把「删除当前版本」理解成旧版本仍保留。

**D2.5 隔离区**（原型要求应用内一键撤销，而 `SHFileOperationW` 无稳定恢复句柄，故删除必须先移入应用管理的隔离区）：

**隔离记录分两类**（D10 收窄后，隔离区不再承担「所有写操作的通用 undo」）：

| 类型 | 用途 | 撤销 |
| --- | --- | --- |
| `undoable_delete` | D10.1 各删除操作 | 保留 5 秒撤销 |
| `transactional_retire` | update / 改类型的旧程序退位 | **仅供失败补偿**；提交成功后立即异步送系统回收站，**不展示撤销**（D10.2：update 不可撤销）。送出失败则保留清单供启动恢复，但**不得**因此重新承诺 update 可撤销 |

- **隔离根位于工作区同卷的受控兄弟目录**，路径由应用生成、不接受用户输入、扫描排除。
- **首批实现不做跨卷分支**：无法建立同卷隔离根 → 返回 `trash_unavailable`。跨卷复制、逐项校验与退位会显著抬高公共基础复杂度，收益不足。
- 持久化操作清单：原路径、内容 hash、状态、时间。
- **撤销窗口届满后异步送系统回收站**，不等应用退出（正常退出可能被大目录清理拖住，崩溃则根本不执行）。崩溃后下次启动按持久化清单恢复处理。
- 撤销目标被占用 → `undo_conflict`，隔离内容不得删除。
- 与 D4 的 `旧版本/` 是两套机制：隔离区是短期删除暂存，`旧版本/` 是用户选择的长期保留，二者保留根、元数据、生命周期均不同。

### D3 新路径准入校验

**规则表述：任何操作要让一个新业务身份占用最终可扫描路径，落盘前必须通过下列全套校验。** 按入口枚举容易漏，以此表述为准。

1. `assert_within_workspace`；
2. 目标不存在——含大小写、junction 等价身份，否则 `path_exists`；
3. 父目录领域归属正确；
4. Windows 文件名校验：非法字符、保留名（`CON`/`PRN`/`AUX`/`NUL`/`COM1-9`/`LPT1-9`）、尾随点与空格；
5. **对最终完整路径执行与 scanner 完全相同的排除判定**（scanner 匹配整个绝对路径，不是只匹配名称）。若 configured root 本身即命中排除关键词 → 直接报告该工作区不可用于写入；
6. `find_dangling_anchors` → `hits` 非空即 `path_identity_conflict`，`issues` 含阻断级一并阻止；
7. **在最终原子提升前、持写锁时再验一次**（防 TOCTOU）。

**不提供强制覆盖。** 用户选择：换名字，或先清理旧借用登记。

已知入口（非穷举）：新建型号、新建方案、新增程序、D1 语义变化的新资产、首次创建的模块叶子、重命名目标、update 的 replacement 提升路径、备用副本恢复/交换的激活路径、解压导入产生的每个资产根。

**例外**（均属原身份延续，走各自的窄化规则，**不得泛化为用户可选的强制覆盖**）：备用副本恢复（D4.4）、删除撤销（D2.4 / D2.4a）、legacy 布局归一（D0.3）。这些场景下命中历史锚点是预期结果；仅当发现 plan 之外的重叠锚点才返回 `path_identity_conflict`。

### D4 `旧版本/` 备用副本

**D4.1 落点**：`<程序目录>/旧版本/<原变体名>-<时间戳>/`。随程序目录移动天然跟随，不产生孤儿。

**`<程序目录>` 指退位完成后的「当前程序」**，不是被退位的那一个：update 退位时是 replacement；恢复交换（D4.4）后是恢复出来的那个程序。**不得把旧程序放进它自己的 `旧版本/`**（自包含移动）。

**D4.2 副本元数据**：记录 `retired_from`（原始身份路径）、内容 hash、退位时间。

**原子边界（不变量，临时目录与写入顺序见实现子 TASK）**：「旧程序内容 + 副本元数据」是**一个提交单元**——先在 staging/temp 内生成并校验元数据，整体原子提升到 `旧版本/` 下。**不得产生没有 `retired_from` 的正式副本**（否则 D4.4 恢复时取不到可信的原始身份路径）。

hash 定义：按「相对路径 + 文件长度 + 文件内容 SHA-256」生成稳定 manifest hash，**排除副本元数据本身，不含 mtime**（否则复制或恢复会无意义失配）。

**D4.3 排除规则**：新增**公开的受管路径判定**，拆成两个函数（单一 `bool` 无法同时承载「跳过」与「按 reason 分流」）——

```
managed_path_reason(path: Path, *, is_dir: bool) -> ManagedPathReason | None
should_exclude_managed_path(path: Path, *, is_dir: bool) -> bool   # 前者的薄包装
```

覆盖：① 精确保留目录段（任一 segment == `旧版本`，Windows 大小写不敏感）；② `程序信息.toml`（文件，非目录段，见 D6.2）；③ staging 与隔离区；④ 其他应用内部清单。

scanner / USB 用 `should_exclude_managed_path`；软件修复用 `managed_path_reason` 按类别分流。

**helper 返回分类 reason，调用方按用途决定「跳过 / 读取元数据 / 报告」**——「遍历时跳过」与「作为用户可见 payload」是两回事：

| 调用方 | 对 `程序信息.toml` |
| --- | --- |
| scanner / USB 复制 | 排除（`FirmwareAsset.files` 也须过滤，否则详情会把内部元数据当程序文件展示） |
| 软件修复 | **允许发现并严格读取**（D7.5 待补齐清单依赖它），但不当作固件 |
| 导入 | 不信任来源内容，读取或忽略后由应用重写 |

四处共用同一 helper，不得各自复制字符串规则。

`SCAN_EXCLUDE_DIR_KEYWORDS` 中的泛化 `"旧"` 作为短期兼容保留，但必须同时：① D3.5 禁止创建会被扫描器排除的路径；②「软件修复」列出因 legacy `"旧"` 被排除的目录；③ 迁移确认后删除该泛化规则。

> 否则 `旧款L36` 这类真实型号目录仍会静默整棵消失——这是现存隐患，不是新引入的。

**D4.4 借用与恢复**：

- 借用锚点落在 `旧版本/` 段内 → 新增专用 issue 类别 **`retired_anchor`**，固化 `anchor_path`、`source_root`、引用方与 raw key。语义：查询目标与 anchor/source 有边界关系时阻止；新建借用不得选中该来源；**无关目标只报告 warning**；**不加入 `BLOCKING_ISSUE_CATEGORIES`**（否则不相关型号的全工作区反查会一起失败）。
- **恢复/交换顺序**（全程持写锁）：
  1. 校验副本元数据，把副本从 `旧版本/` 提升到其 `retired_from`；
  2. 此时 old 与 replacement 同为合法现存资产 → `build_rewrite_plan` / `apply_rewrite_plan`（R8 update）；
  3. apply 成功后，把当前程序移入恢复后程序的 `旧版本/`；
  4. 最后对两路径的共同祖先对账（`reconcile_subtree`）。

  **失败补偿必须分阶段**（统一「把副本移回」会在 apply 成功后立即造成断链——此时引用与 defaults 已指向恢复后的资产）：

  | 失败点 | 处理 |
  | --- | --- |
  | 步骤 2 的 build/apply 之前 | 副本移回 `旧版本/` |
  | apply **完整回滚成功** | 副本移回 `旧版本/` |
  | apply 出现 **rollback conflict** | **停止移动**，返回 `restore_inconsistent` |
  | apply 成功、步骤 3 退位失败 | 保留两个活动程序，返回 `retire_failed`，**不得**把 replacement 移回 |
- 只允许恢复到 `retired_from` 记录的原始身份路径；命中该原路径的历史锚点属**预期恢复**，不算新身份复用；目标已存在、元数据不符、范围重叠仍阻止。

**D4.5 必须修的实际缺陷**：`copy_directory_to_usb` 无 `ignore`，`旧版本/` 与 `程序信息.toml` 会被拷进 U 盘。改用 D4.3 helper，回归测试须覆盖：嵌套 `旧版本`、大小写变体、同名**文件**不误排、`旧版本说明` 之类前缀不误排。

### D5 机芯类型 ↔ `[[platform]]`

**D5.1 权威字段**：机芯类型是型号级属性，唯一权威落在型号根 `平台配置.toml` 的 `[[platform]].name`。枚举 `单3D` / `单2D` / `双2D` / `上3D下2D`。资产侧派生为 `chassis_type`（D0.1）。

**D5.2 新建型号写单块**，`defaults` 初始为空。型号建成后机芯类型不可改（原型：方案「随型号确定」）；改机芯类型 = 建新型号。

**D5.3 与 `方案配置.toml.platform` 的关系**：新建方案不写该字段。它是 legacy 分块来源，新数据不再产生。

**`ensure_platform_blocks` 必须改造或退出新写路径**——不能依赖「偶然是 no-op」：现有型号只要保留任一带 `platform` 的 legacy 方案，它仍会追加块。正式 CRUD 入口不得再从方案 `platform` 扩充 block。

**D5.4 存量多块不整型号封锁**——只阻止「必须猜测目标块」的操作：

| 操作 | 多块时 |
| --- | --- |
| 设为默认 | 阻止，要求先归一 |
| 新建 defaults 键且无明确块 | 阻止 |
| 修改机芯类型 | 阻止（本就不支持） |
| 无法精确定位块的迁移 | 阻止 |
| R8 已按 `block_index` 精确命中的 rename/update | 允许 |
| 厂商更新、不碰平台配置的写操作 | 允许 |

**D5.5 存量归一入口**（放「软件修复」）：展示现有块与冲突 → 用户选定机芯类型 → 合并为单块 → 逐模块处理 `defaults` 冲突。

- **归一前必须先完成 `follow_default` 迁移**（R8 `migrate_follow_default_refs`）：合并并删除 legacy 块后，未迁移的 `follow_default` 会失去 `source_platform` 指向的来源块。目标型号相关的 `follow_default` 存在 unresolved/failed 时**阻止归一**。
- legacy `方案配置.toml.platform`：**保留不动**（避免改写大量存量方案文件）。精确含义——① 不再用于创建 `[[platform]]` block；② 不再用于 `chassis_type`；③ **仍由 legacy `FirmwareAsset.platform` 生产链读取**（D0.1 已定 `_infer_asset_context` 不改），直至该字段另行退役。
- 归一完成后限制 `set_default_variant` 不得创建枚举外或非当前机芯类型的新块，防止低层 API 重新制造多块。

### D6 归属厂商

**D6.1 名单**：`config.toml` 新增 `vendors: list[str]`，缺省 `["摩众", "国瑞", "亿微", "明锐"]`。设置页可追加。

- 规范化：trim 后不得为空；按 Windows/UI 语义 casefold 去重，保留首次输入的展示大小写；
- 配置损坏或非列表时**不得静默覆盖整个 `config.toml`**；
- **删除厂商仅从候选名单移除，绝不改写现存资产**；现存资产允许显示不在当前名单中的历史值。

**D6.2 资产字段落点：程序目录内独立 `程序信息.toml`**，起步仅 `vendor = "摩众"`。

随资产目录移动、退位、恢复天然跟随，不给 R8 增加第三类级联目标，也避开路径作键的大小写/分隔符/canonical 别名/跨文件 CAS 问题。代价是每个已匹配资产多读一个极小文件。

- 缺文件 = legacy / 未知厂商；
- 写入用原子替换；解析损坏 → 资料更新失败并保留原文件，不静默覆盖；
- **纳入 D4.3 排除**（USB 复制、`FirmwareAsset.files` 均须过滤）；
- 导入来源自带同名文件时不得直接信任，由应用按用户选择重写；
- 暂不加格式版本字段，解析保留未知键。

**D6.3 vendor 缺省值**：存量 / 元数据缺失 → `FirmwareAsset.vendor = ""`；**新建程序必须写入用户选择值**，UI 默认名单第一项（原型规则）。

**D6.4 索引与 schema**：`vendor` 与 `chassis_type`（D0.1）同批纳入索引列，**一次性提升 `asset_index.schema_version`**，走既有「不匹配即要求重扫」路径。

迁移提示须说明：目录与 TOML 不受影响，只重建搜索缓存；首次打开给出一次明确的重扫操作，**不得表现成「数据库损坏」**。

### D7 导入与目录成形

**D7.1 staging**：所有导入先落扫描排除的 staging 目录，**完成来源安全与目录结构校验后**提升到最终路径；**catalog 完整性按 D1.5 / D7.5 分流**（普通新增允许 incomplete，update 的 replacement 必须完整）。失败清理 staging，不留半成品。

**D7.2 成形规则**（**剥一层包装、保留内部相对结构**，绝不递归扁平化）：

| 来源 | 规则 |
| --- | --- |
| 单个/多个文件 | 放入新建的资产目录 |
| 文件夹 | 目标资产目录**替代来源目录这一层**，内部子目录原样保留 |
| 压缩包 | 解压后同「文件夹」规则；**仅当根下恰好只有一个目录且无同级文件时**剥掉这一层 |

最多剥一层。空的单一顶层目录按同一规则处理。

**D7.3 来源边界防护**：

- 压缩包：每个条目最终路径必须落在 staging 内；拒绝 `..`、绝对路径、符号链接、**UNC、盘符路径、ADS 冒号、Windows 保留名、尾随点/空格、大小写等价重名**；
- 限额：解压后总字节数、单文件大小、文件数、压缩比，超限返回 `archive_limit_exceeded`；
- **文件夹来源同样拒绝所有 reparse point**（junction / 符号链接），并逐项确认源路径仍在选定来源根内。

**D7.3a 来源与目标重叠**：**导入始终是复制，绝不修改来源。** 拒绝下列情形——

- 来源与目标 / staging 身份相同；
- 来源包含目标，或目标包含来源；
- 来源位于任何受管 staging、隔离区或 `旧版本/` 内；
- 来源在遍历期间发生身份或大小变化（检测到即中止提交）。

**D7.4 重名文件**：同一资产目录内重名 → 拒绝并列出冲突项，不自动改名、不静默覆盖。

**D7.5 手控 UI 缺文件：按原型不阻断保存**，但须闭合技术契约（否则目录不进索引，用户在 CRUD 界面既删不掉也更新不了，「用更新程序补入」没有可选中的资产）：

- **incomplete 目录不提升到最终路径**，留在**受管候选区**，完整后才提升。服务返回 `ok=True, code="created_incomplete"`；

  > 若提升到最终路径，补齐后「重新发起 update」会因该路径已存在而被 D3 的 `path_exists` 必然阻断——流程走不通。留在候选区则补齐后走正常新增提升路径，无冲突。

  **候选区边界（不变量，物理位置与 TTL 见子 TASK 1）**：
  - 应用内部区域，**不可扫描、非业务身份**，路径**由应用生成**，用户来源不得直接选中；
  - scanner、USB 复制、普通导入一律排除；`managed_path_reason` 独立返回 `incomplete_candidate`；
  - 只有「补充文件」服务与 `scan_incomplete_imports` 可读写；
  - **候选路径不执行 D3 的「父目录领域归属」与 dangling-anchor 检查**（它不在 `通用`/`定制` 结构内）；
  - **最终业务路径仍须在首次保存与正式提升前各执行一次完整 D3**。

- **「补充文件」是一次真实写操作**，需独立事务契约：默认**禁止覆盖已有文件**；staging 合并验证；CAS 提交；失败回滚；完整后**原子更新 `import_state`**，再扫描并按新增意图继续；
- 记入**独立的「待补齐」清单**，不伪装为 `FirmwareAsset`；
- **清单真源在磁盘**——扩展 `程序信息.toml`（D6.2）承载：

  ```toml
  vendor = "摩众"
  intended_firmware_type = "handcontrol_ui"
  import_state = "incomplete"
  ```

  **需新增独立入口 `scan_incomplete_imports`**——普通 scanner 只有 catalog 匹配后才构造资产，而 incomplete 手控目录恰恰匹配不上，无法靠它重建。该入口遍历受管候选区并按元数据识别；补齐后重新验证 catalog，成功才转为资产；元数据悬空、目标丢失或内容已变时给出诊断。

  **候选项不保存旧操作意图**：候选项只代表「一份待补齐的内容」，**不持久化** create / update / change 的意图、旧资产身份或过期的操作计划。用户补齐后**重新选择**是新增还是更新、以及最终落点。

  > 保存意图会引入过期计划问题（旧资产可能已被删除或改名），而重新选择既简单又与「补齐后重新发起 update」一致。

  **可发现性不变量**：候选目录在**任何中间状态下崩溃后都必须能被恢复扫描发现**，不得出现「普通 scanner 排除它、候选 scanner 又不认它」的双盲区。具体用状态字段还是日志状态实现，留给子 TASK 1（见「下放到实现子 TASK 的不变量」）。

  **不得只放内存**（重启即丢）**或只放 SQLite**（schema 重建即丢）。补齐后删除或更新 `import_state`。
- 「软件修复」与新增结果页必须提供「打开 / 补充文件 / 删除 / 重新检测」入口；
- **D1 的 update/改类型场景若 replacement 不完整，只保存为待补齐项，绝不退位旧程序、绝不改写引用或 defaults**（见 D1.5）；
- 补齐 `.rom` + `.pkg` 后再进入正式索引与 update 提交阶段。

**D7.6 介绍文件**：随程序一起保存，不在界面展示（原型规则 46）。

### D8 工作区读写锁

- **跨进程读写锁 + generation 令牌**，锁键由 configured root 的规范身份派生。
- CRUD 提交持**排他锁**；权威扫描/索引写入持排他锁；**纯预览扫描不持锁**，但结果提交前必须重验 generation（否则长扫描会封锁 CRUD）。
- 锁外允许预览/构建计划；提交时在锁内重验（同 D3.7）。
- **等待用户确认及 5 秒撤销窗口期间不得持续占锁**；真正提交/撤销时重新获取并重验。
- 定义超时、abandoned lock 恢复与不可重入规则。获取失败返回 `workspace_busy`。

**D8.1 generation 持久化**（只靠进程内计数则跨进程与崩溃恢复均不成立）：存于**受控状态文件**，原子递增。

**采用 seqlock 语义**（只在操作完成后递增，无锁预览会读到 D1.1 步骤 5 与 6 之间的中间态，发布出「default 已清、旧仍存在」）：

- 第一次产品数据变更**之前**递增为**奇数** = 写入中；
- 成功、失败或 inconsistent 收尾时再次递增为**偶数**；
- **预览仅当开始与结束 generation 相同且为偶数时才可发布**；
- 遗留的奇数状态由启动恢复流程处理：**发现奇数 generation 后，恢复完成前所有预览与写操作一律返回 `workspace_recovery_required`**，不得由新写操作把奇数直接推进。

**任何已改变磁盘或 TOML 的操作，即使最终返回 inconsistent，也必须完成递增**（结束 seqlock）；但「能否继续写」由 D8.4 的 `WorkspaceState` 决定，不由 generation 奇偶决定。

**D8.3 复合写操作共用事务协调器**：D0.3 布局归一、D1.1 改类型/改范围、**D1.4a 普通 update**、D2.1/D2.2 创建、D2.3 重命名、D2.4/D2.4a 删除、D4.4 恢复交换、D9.3 工作区布局迁移**全部接入同一协调器**（持久化操作日志 + 阶段标记 + 启动恢复），并各自列出恢复状态。不得只给 D1.1 写恢复逻辑。

**D8.4 工作区状态与 generation 分离**（只靠 seqlock 奇偶不足：`*_inconsistent` 收尾也要推进为偶数，否则 seqlock 永不结束，但偶数又意味着「可发布」，现场会被当成正常状态放行后续写入）：

独立持久化 `WorkspaceState = Literal["clean", "operation_in_progress", "recovery_required"]`：

- generation 恢复为偶数以**结束 seqlock**；
- 但只要状态是 `recovery_required`（`rename_inconsistent` / `update_inconsistent` / `layout_inconsistent` / `restore_inconsistent` 等现场），**所有新写操作一律阻止**；
- 预览：只读放行但必须带警告（不阻止用户查看现场）；
- 恢复完成、或用户明确确认已人工修复后，才切回 `clean`。

**两条不变量**（精确落盘顺序与原子替换见子 TASK 1）：① **产品数据变更前必须先进入非 `clean` 状态**——不得出现「数据已开始变化、磁盘状态仍是 `clean`」；② **不一致现场不得重新开放写入**。

**D8.2 内部目录所有权**（公共基础子 TASK 一次性定义，不散落各处）：

| 目录 | 位置 | 生命周期 |
| --- | --- | --- |
| staging 根 | 工作区内同卷 | 单次操作，失败即清 |
| 隔离根 | 工作区同卷受控兄弟目录 | 撤销窗口 + TTL，届满异步送回收站 |
| `旧版本/` | 资产目录内部 | 用户长期保留，不自动清 |
| generation / 操作日志 / 隔离清单 | 受控状态位置 | 随工作区 |

须一并定稿：每种目录**允许哪些服务写入**、启动恢复顺序、TTL 与清理规则；所有内部路径由应用生成并经**专用守卫**。

> `should_exclude_managed_path` 只解决「扫描与复制时跳过」，**不等于授权写入**这些目录——两者是不同的判定。

### D10 撤销范围

原型 `apply()` 原先包裹全部 15 处写操作（snapshot/restore），即承诺「所有写操作可撤销」。**本任务收窄为：只有删除类操作可撤销。**

**D10.1 可撤销**：

| 操作 | 原型位置 | 逆操作 |
| --- | --- | --- |
| 删除程序 | `:1685` | 隔离区目录移回原路径 |
| 删除型号 | `:1195` | 同上 |
| 删除方案 | `:1294` | 同上 |
| 删除备用副本 | `:1646` | 同上 |
| 删除待补齐项（D7.5） | 新增 | 同上，撤销后重新进入 `scan_incomplete_imports` |
| 解除借用 | `:1664` | **恢复 `型号配置.toml` 条目**（不涉及任何文件移动） |

**D10.1a 解除借用的撤销契约**（`clear_shared_module` 当前是无 preimage 的幂等 TOML 条目删除，**不能原样复用**）：

- clear 前保存完整 preimage / postimage；
- **当前文件仍等于 postimage 时才允许恢复**；
- 期间用户已登记其他借用或修改了 TOML → `undo_conflict`；
- 5 秒窗口届满即丢弃 undo preimage；
- 严格读取失败时不执行 clear。

**D10.1b 删除最后一个变体后的撤销**：D2.4a 步骤 7 会自动 `rmdir` 空模块容器，撤销时父目录已不存在。隔离清单须**记录本次自动删除的空父目录**；撤销时先重建模块容器，再移回 asset。父路径已被其他身份占用 → `undo_conflict`，隔离内容保留。

**移回前必须核验隔离内容的 manifest 与清单状态**，不一致 → `undo_conflict`，避免把隔离区里被外部改过的内容恢复回工作区。

**D10.1c 待补齐项删除**（incomplete 不是 `FirmwareAsset`，不能调 `find_references_to(..., "asset")`）：严格读取受管元数据并验证 `import_state == "incomplete"` → 不做 R8 asset 反查，但仍过路径守卫与状态 CAS → 移入可撤销隔离区。

**D10.2 不可撤销**——提交后即生效，提示条只报告结果、不带「撤销」按钮：

| 操作 | 原型位置 | 用户的替代路径 |
| --- | --- | --- |
| 新建型号 / 方案 / 程序 | `:1148` / `:1243` / `:1487` | 删除刚建的对象（本身可撤销） |
| 重命名程序 / 型号 / 方案 | `:901` / `:1176` / `:1272` | 再改回原名 |
| 设为默认 | `:906` | 重新设为原来那个 |
| 更新程序（含仅改厂商） | `:1614` | 恢复备用副本，或再更新一次 |
| 登记借用 | `:1509` | 解除借用（本身可撤销） |
| 恢复备用副本 | `:1641` | 反向再交换一次 |
| legacy 模块叶子归一 / 工作区布局迁移 | D0.3 / D9.3 | 无（一次性操作，操作前需确认） |

**D10.3 原型须同步修改**：原型共 **15 个 `apply(...)` 调用点**（不含 `apply` 函数定义本身）。D10.1 的 5 处保留撤销，其余 **10 处**改为不带 undo 回调——`:901`（重命名程序）、`:906`（设为默认）、`:1148`（新建型号）、`:1176`（重命名型号）、`:1243`（新建方案）、`:1272`（重命名方案）、`:1487`（新增程序）、`:1509`（登记借用）、`:1614`（更新程序）、`:1641`（恢复备用副本）。

实现方式：`apply(mutate, message, detail, undoable = false)`，仅 D10.1 五处传 `true`。

**厂商名单增删（D6.1）不可撤销**：保存失败保留原 `config.toml`，用户可再次添加或删除候选项。

> 理由：新建的「撤销」实质就是删除、更新的「撤销」实质就是恢复备用副本——原型里这两条路径本来就有独立入口，做成撤销是重复路径。而为每类写操作定义文件系统逆操作、CAS 条件与窗口清理，成本远高于收益。删除是唯一「用户可能误触且没有等价补救入口」的操作，因此保留撤销。

### D9 工作区容器、型号 CRUD 与旧布局迁移

**D9.0 布局判定是公共能力**：定义 `WorkspaceLayout = Literal["single_model", "multi_model", "empty", "invalid"]`，型号 CRUD、scanner、reference lookup、`chassis_type` 派生与 UI 使用统一检测结果。

- `single_model` 仅指旧布局「工作区根本身就是型号」，不表示工作区里恰好有一个型号。
- `multi_model` 指「工作区/型号子目录」结构，包含一个或多个型号；`empty` 指合法工作区中没有型号，受管目录不计入型号数量。
- 无效或混合布局为 `invalid`，不得当空工作区初始化；判定及冲突诊断在子 TASK 1 定稿。

**D9.1 工作区是稳定容器，开放型号级 CRUD。**

- 新建、重命名、删除型号仅作用于工作区下的型号目录；工作区根路径与配置保持不变。
- 删除最后一个型号后，保留工作区根与受管状态，显示空工作区并保留「新增型号」入口；删除仍按 D2.4 / D10.1 支持撤销。
- 新建空白型号只需名称、机芯类型和 D2.1 规定的基础目录与配置，不要求先有方案或程序。型号列表以型号目录及配置为依据，不依赖资产索引中是否有行；重启后空白型号仍可见。
- 删除程序或方案导致型号内没有资产时，不自动删除型号。扫描零资产也不等于没有型号。

**D9.2 旧布局先适配，再执行型号级操作。**

现有 `enumerate_model_roots` 在根自带型号标志时直接返回根，不能在其下直接创建第二个型号；也不能把配置根作为型号删除或重命名的目标。旧布局中的型号级入口引导执行 D9.3 迁移，迁移成功后重新预览并执行原操作，不长期禁用功能。方案与程序的既有操作继续兼容旧布局。

**D9.2a 借用按可用来源数量判断**：

- 排除借入方后没有有效来源型号时返回 `no_other_model`，不按布局枚举或总型号数静态禁用。
- service 独立校验来源与借入型号身份相同的情况，返回 `self_reference`，不只依赖 UI 过滤。
- 空白型号没有可借用的程序；新增其他型号及其程序后可成为来源，无需重新开启功能。
- 既有借用的解析与解除（D10.1）继续可用。

**D9.3 旧工作区布局迁移纳入本轮 CRUD，由子 TASK 3a 实现。**

- 在同一配置根内，把旧型号所属内容归入一个型号子目录，形成「工作区/型号」结构；不切换到父目录、不纳入工作区外的兄弟数据。
- 迁移前展示目标名称、路径变化和影响；取消或预检失败时零写盘。文件归属不明、名称或路径冲突时阻止并给出具体原因，不能直接把整个根递归搬进自身子目录。
- 保留 `model_id`、程序内容、方案归属、默认与借用语义；同步受影响的路径引用及缓存，并对整个工作区重扫对账，清除旧路径索引和隐藏项残留。不以迁移重置厂商或机芯类型。
- 受管目录与工作区状态不随型号搬移。已有候选、隔离或恢复记录不得失去归属；其路径适配与迁移准入条件在子 TASK 3a 定稿。
- 接入 D8 事务协调器：中断后恢复到完整旧布局或完整新布局；无法恢复一致时进入 `recovery_required` 并阻止后续写入。具体移动步骤、路径映射、错误码与崩溃点测试由子 TASK 3a 在编码前定稿审查。
- 迁移是独立操作；成功后再执行原型号操作，后续操作取消或失败不回退已成功的迁移。迁移成功不提供撤销按钮，失败补偿按事务契约处理。
